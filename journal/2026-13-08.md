# 2026-08-13

## Request

Update the `debug-ticket` workflow to query AWS CloudWatch logs as the second step, immediately after reading the JIRA bug ticket.

## Reasoning

The existing workflow ran five phases: Triage → Resolve repo → Investigate → Verify → Report. CloudWatch log evidence is independent of the GitLab repository. Querying it before cloning the repo means the three investigation lenses (recent-changes, code-path, pipeline-ci) receive concrete log evidence — timestamps, error counts, sample lines — which tightens their candidate search. Inserting CloudWatch between Triage and Resolve repo is the correct ordering because:

1. The triage output supplies the component name, environment, reported date, and verbatim error strings that drive the log query.
2. CloudWatch results are non-blocking: if the AWS CLI is absent or credentials are missing, the workflow continues with a note.
3. All downstream agents (lenses, skeptics, report) benefit from log evidence without needing to query CloudWatch themselves.

## Accepted solution

The user approved the plan without modification. The following changes were made to `.claude/workflows/debug-ticket.js`:

1. Added `{ title: "CloudWatch", ... }` to `meta.phases` between Triage and Resolve repo.
2. Added `cloudwatchSchema` — structured output fields: `queried`, `error`, `logGroups`, `errorPatterns` (pattern, count, firstSeen, lastSeen, sampleMessage), `timeWindow`, `notes`.
3. Added `cloudwatchPrompt(triage)` — instructs the agent to check AWS CLI availability, infer log groups from component/environment, query `aws logs filter-log-events` over a ±24/48-hour window around the report date, and return findings without writing to any AWS resource.
4. Inserted `const cloudwatch = await agent(cloudwatchPrompt(triage), ...)` in the execution body between the Triage and Resolve repo phases.
5. Updated `ticketContext(triage, repo, clonePath, cloudwatch)` — added a new `cloudwatch` parameter; the function now inlines CloudWatch findings into the context block passed to every lens and skeptic agent.
6. Updated `lensPrompt`, `skepticPrompt` — both now accept and forward the `cloudwatch` argument to `ticketContext`.
7. Updated `reportPrompt(ticket, triage, repo, findings, clonePath, cloudwatch)` — added a `CLOUDWATCH FINDINGS` block and a new report section 2 "CloudWatch findings". Section numbering shifted from 5 to 7.
8. Updated the `phase("Investigate")` and `phase("Verify")` agent calls to pass `cloudwatch` through.
