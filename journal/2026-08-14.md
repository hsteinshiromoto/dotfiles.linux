# 2026-08-14

## Request

Update the `debug-ticket` workflow. After it reads the JIRA card, and before it reads CloudWatch, it must log in with `aws sso login --profile <environment>`. Read `~/.aws/config` for the profiles and environments.

## Reasoning

The CloudWatch phase assumed a valid AWS session. When the SSO token was expired, the phase failed inside the agent and returned `queried=false`. The report then said "not available" for a problem a login solves.

`~/.aws/config` defines eight profiles on one SSO session (`d-97674299db`):

| Profile | Region | Environment |
| --- | --- | --- |
| `prod` | ap-southeast-2 | production, AU |
| `produk` | eu-west-2 | production, UK |
| `preprod` | ap-southeast-2 | pre-production |
| `qa02` | ap-southeast-2 | QA |
| `dev02` | ap-southeast-2 | development |
| `test` | ap-southeast-2 | test, AU |
| `testuk` | eu-west-2 | test, UK |
| `sandbox` | ap-southeast-2 | sandbox |

Three constraints shaped the design:

1. `aws sso login` opens a browser and waits for a human. A subagent that runs it with no valid session hangs the workflow. The step therefore tests the session first and logs in second.
2. A login the agent cannot verify is worse than no login. The step confirms every session with `aws sts get-caller-identity` before it reports success.
3. A failed login must stop the workflow, not degrade it. Querying CloudWatch with dead credentials produces an empty result that reads like an absence of errors.

## Accepted solution

The user approved the change. These changes went into `.claude/workflows/debug-ticket.js`:

1. Added `{ title: "AWS login", ... }` to `meta.phases`, between Triage and CloudWatch. Updated `meta.whenToUse` for the new optional `profile` argument.
2. Added the `AWS_PROFILES` table — the eight profiles with region and environment hint. The prompt tells the agent to read `~/.aws/config` and trust that file over the table.
3. Added `awsLoginSchema` — `loggedIn`, `profile`, `region`, `account`, `profileEvidence`, `alreadyValid`, `error`.
4. Added `awsLoginPrompt(triage, override)`. It matches the profile on the ticket `environment` field first, then on `component`, and reads "UK" or "eu-west" as a UK profile. It defaults to `prod`. It tests `aws sts get-caller-identity` before it runs `aws sso login`, gives the login a 120 second timeout, forbids `--no-browser`, and confirms the result with a second identity call.
5. Inserted the `phase("AWS login")` agent call before the CloudWatch phase. A failure returns `status: "aws_login_required"` with a `remedy` field holding the exact command, and logs the same line.
6. Updated `cloudwatchPrompt(triage, aws)` — it now receives the profile and region, passes `--profile` on every `aws` command, and must not run `aws sso login` or `aws configure` itself.
7. Updated `cloudwatchReportPrompt(ticket, triage, cloudwatch, aws)` — added an `AWS SESSION` block. Report section 2 now names the profile, region, and account searched.
8. Extended the `READ_ONLY` block. The SSO token cache under `~/.aws/sso` is the third permitted write, with the scratch clone and the report file.
9. Added the profile and account to the workflow return value.

Added five AWS permissions to `.claude/settings.local.json`: `aws --version`, `aws sso login --profile *`, `aws sts get-caller-identity --profile *`, `aws logs describe-log-groups *`, and `aws logs filter-log-events *`.

## Sanity check

No automated test suite covers workflow scripts. Three checks ran instead:

| Check | Result |
| --- | --- |
| `node --check` on the async-wrapped script | PASS |
| Grep for `Date.now`, `Math.random`, `new Date()` | None found |
| Stub-harness run of all three control-flow paths | PASS |

The harness stubbed `agent()` and drove three cases. A successful login reached all four agents and returned `cloudwatch_only` with the profile and account. A failed login stopped after two agents and returned `aws_login_required` with the remedy command. A dead login agent took the same path and defaulted the profile to `prod`.

Verdict: PASS.
